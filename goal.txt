Build a Python experiment harness to compare two document-processing architectures using Google Gemini 2.5 Pro multimodal API.

GOAL
I want to quantitatively compare:

Approach A — Extract once:
1. Send the original PDF/image to Agent 1.
2. Agent 1 extracts the document text.
3. Store that extracted text in state.
4. Agent 2, Agent 3, etc. receive ONLY the extracted text.
5. Agents run sequentially.

Approach B — Reprocess the document:
1. Agent 1 receives the original PDF/image.
2. Agent 2 receives the same original PDF/image.
3. Agent 3 receives the same original PDF/image.
4. Every agent independently processes the original document.
5. Agents run sequentially.

IMPORTANT:
- Do NOT introduce a hybrid approach.
- The purpose is purely to measure the differences between these two approaches.
- Use Gemini 2.5 Pro.
- Make the number of agents configurable; default = 3.
- Make the input document folder configurable.

DUMMY AGENTS
Create simple dummy agents so that the experiment focuses on token usage and latency rather than business logic.

For example:
Agent 1: Document extraction / validation
Agent 2: Document classification
Agent 3: Schema extraction

The exact agent prompts should be configurable.

For Approach A:
- Agent 1 receives the original document and produces extracted text.
- Agent 2 onward receives the extracted text.
- The extracted text should be reused exactly as returned by Agent 1.

For Approach B:
- Every agent receives the original document as multimodal input.

METRICS
For EVERY Gemini API call, capture:

- document_name
- approach
- agent_name
- agent_number
- start_time
- end_time
- latency_seconds
- input_token_count
- output_token_count
- total_token_count, if available
- model_name
- success/failure
- error message, if any

Also calculate for each document:

- total end-to-end latency
- total input tokens
- total output tokens
- total tokens
- number of Gemini calls

And calculate aggregate statistics across all documents:

- mean latency
- median / P50 latency
- P95 latency
- mean input tokens
- mean output tokens
- total tokens
- average tokens per document
- percentage difference between Approach A and B

LATENCY
Measure actual wall-clock latency around every Gemini API call using Python's time/performance counter.

I specifically want to understand the impact of repeatedly loading/parsing the original document, so do NOT artificially remove document-loading time from the measurement. Clearly separate:
1. document preparation/loading time, if measurable
2. Gemini API latency
3. total agent latency

TOKEN USAGE
Use the token usage information returned by the Gemini API rather than estimating token counts wherever possible.

For multimodal PDF/image inputs, record whatever input-token/usage metadata Gemini actually reports.

For Approach A, make sure the 700-token extracted text (or whatever Gemini actually returns) is counted as output from Agent 1 and then as input to downstream agents.

OUTPUT
Create:

1. A clean Python script, e.g. `gemini_architecture_benchmark.py`
2. `requirements.txt`
3. `README.md` explaining setup and execution
4. CSV containing one row per Gemini API call
5. CSV containing one row per document/approach with aggregated metrics
6. A final comparison summary showing Approach A vs Approach B.

CONFIGURATION
Use environment variables for credentials. Do NOT hardcode API keys.

Support something like:

GEMINI_API_KEY=...

Also allow:
- model name
- input folder
- number of agents
- output folder

REPRODUCIBILITY
Use the same documents and equivalent prompts for both approaches.

Run each approach sequentially on the same documents.

If possible, allow multiple runs per document so I can calculate variability in latency and token usage.

ERROR HANDLING
If one agent fails:
- record the failure
- record the latency and available token usage
- continue with the next document
- do not silently discard failures.

At the end, print a concise report such as:

Avg latency X sec Y sec

P95 latency X sec Y sec
Avg input tokens X Y

Do not make assumptions about Gemini token pricing. The experiment should primarily measure actual token usage and latency. Keep pricing calculation as an optional configuration.

Please write production-quality, readable Python with clear functions/classes, type hints where useful, logging, error handling, and comments explaining the experiment design.
